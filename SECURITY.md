| Finding ID | Severity | Risk Identified | Resolution & Verification | Status |
| :--- | :--- | :--- | :--- | :--- |
| **SEC-19** | **CRITICAL** | In-process idempotency mutex and in-memory campaign queue are unsafe on Cloud Run: multiple replicas and independent restarts could duplicate campaigns and notifications, and a crash lost all queued work. | Durable database-backed idempotency: `notification_campaigns.idempotency_key UNIQUE` + atomic `INSERT ... | **SEC-30** | **LOW** | A regenerable demo SQL dump was committed under `backups/`, establishing a pattern where backup artifacts (which may contain real user data once production backups begin) enter Git history and Docker build contexts. | The committed dump was removed from the branch (it is regenerable via `npm run db:backup`), and `backups/` plus `*.dump` are now ignored in `.gitignore` and excluded in `.dockerignore`. | **SEC-31** | **HIGH** | The public health probes sat behind the standard rate limiter, whose store is PostgreSQL-backed: during a database outage the limiter's `increment()` threw and express-rate-limit failed the request, so even the process-only `/api/v1/health/live` returned 500 instead of 200 — liveness was not actually database-independent (restart-storm risk on Kubernetes/Cloud Run). Honest at-least-once disclosure: FCM delivery deduplication is durable (one campaign per idempotency key, one receipt per notification × device), but external FCM semantics cannot guarantee exactly-once delivery; a rare FCM-side duplicate after a network-level retry is possible and documented rather than hidden. Additionally, a worker crash in the window between FCM accepting a message and the delivery receipt being written in PostgreSQL is recovered by stale-claim reclamation (the campaign is re-queued after 5 minutes and re-processed); within that window the same device can receive the same push twice, and the re-run's receipts deduplicate via the `UNIQUE (notification_id, device_id)` constraint. The system therefore provides at-least-once delivery and never claims exactly-once.

## 2. Defense-in-Depth Architecture

### 2.1 Identity & Authentication
- **Firebase ID Token + Revocation Verification**: Every protected backend route requires `Authorization: Bearer <Firebase_ID_Token>` verified via `adminAuth.verifyIdToken(token, true)`.
- **Zero Impact on Existing Flows**: Existing Google Sign-In, Email/Password login, password reset, guest mode, and Firestore game saves on `Arrow Out` and `Crystal Quest` remain untouched.

### 2.2 Role-Based Access Control (RBAC) & Data Isolation
- **`user` Role**: Can register/revoke only their own FCM device tokens (`userId === req.user.uid`) and read/update only their own per-app notification preferences (`prefId === ${uid}_${appId}`).
- **`admin` Role**: Verified server-side via `/admins/{uid}` and verified root admin email (`aaryapratik@gmail.com`). Required for broadcasting notifications, modifying app-level rate limits, reading documentation blueprints, and inspecting security audit logs.

### 2.3 Network, Rate Limiting & Input Hardening
- **Anti-Spoofing Rate Limiters**:
  - `standardApiLimiter`: 180 req/min/IP keyed by `extractTrustedClientIp(req)`.
  - `sensitiveMutationLimiter`: 30 req/min/IP on `/api/v1/auth/verify`, `/api/v1/notifications/send`, `/api/v1/apps`, `/api/v1/devices`, and `/api/v1/preferences`.
- **Strict Zod Schemas (`.strict()`)**: Rejects shadow/unknown fields (`unrecognized_keys`) and strips `<script>`, `javascript:`, and inline `on*=` event handlers.
